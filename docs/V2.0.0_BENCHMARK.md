# v2.0.0 benchmark evidence

The v1.1.0 run compared two skills on the same brief. The v2.0.0 run asks a different question: **does the pipeline hold end to end?** It uses the same unchanged Orbit One base prompt from [comparison test](COMPARISON_TEST.md), but routes it through the whole v2 chain — contract, studio, human review, handoff, build, review — instead of handing it straight to one specialist.

This document records what has been verified. It is written as the run proceeds, and it distinguishes what was measured from what is still outstanding.

## Stage 2 — Design system round trip

`ls-design-studio tokens --emit stitch` produced a variant of the contract with the `dark-` prefixed tokens stripped. The stripped document contains **zero** `dark-` keys in its frontmatter, and the one remaining occurrence of the string in the file is a sentence of prose explaining the convention.

That document was uploaded to the generator, a design system was created from it, and the design system was applied to every generated screen. The generator's own record of the design system carries the contract's exact hex values and type scale.

**One fidelity gap, recorded rather than hidden:** the generator substituted `Newsreader` for the contract's `Instrument Serif` in its headline slot, because the contract's face is not in its font set. Every colour, radius and spacing value survived unchanged. The build stage uses the contract's font, not the generator's substitute, so this affects the design-phase screens only.

## Stage 3 — Screens and the review loop

Three desktop screens were generated, covering all nine required sections of the base prompt.

| Screen | Sections | Revisions | State |
|---|---|---|---|
| `home-header-hero-story` | 1 header, 2 hero, 3 product story, 9 footer | r2 | pending human review |
| `features-materials-colourways` | 4 features, 5 materials, 6 colour selector | r2 | pending human review |
| `specifications-purchase-footer` | 7 specifications, 8 purchase call to action | r1 | pending human review |

Both revisions were produced by the loop working as designed. In each case the agent ran a check against the contract, recorded a rejection with a note, the studio queued a request carrying that note verbatim, the agent claimed it, sent it to the generator as an edit, posted the result as a new revision, and resolved the request.

**What the agent's contract check caught, and the generator fixed:**

| Screen | Finding | Fixed in |
|---|---|---|
| home | Story invented "advanced computational audio", "precisely angled custom drivers", "wide, immersive soundstage" | r2 |
| home | Said "sand-blasted aluminum" where the facts say recycled aluminum | r2 |

| features | The product under the selector was an empty wireframe, not the selected colourway | r2 |

Every one of these is a fabrication or a contract deviation that a prose-only suite would have shipped, because v1.x had no artifact to check against and no place to record the finding.

## Stage 4 — The approval gate

**Complete.** All three screens were approved by the person in the studio on 2026-09-02 at 22:49 UTC, and the gate released the handoff.

The invariant held throughout. An approval attributed to the agent is refused:

```text
POST /api/screens/scr_1dfbae81/decision {"state":"approved","by":"agent"}
E_GATE_BLOCKED - an agent cannot approve a screen; approval is the person's decision in the studio
```

Every recorded approval carries `by: "human"`. An agent *rejection* is accepted and attributed to the agent.

The gate opened only once there was at least one screen, every screen was approved, nothing was stale against the current tokens, and no token reapplication was queued:

```text
gate: passed=True canPass=True pending=[] rejected=[] stale=[] pendingReapply=0
handoff sha256: 3e2114d1c7f69a99...
19 files, all digests verified with sha256sum -c
```

### Screens rebuilt as token-driven before approval

The three screens originally came from an external generator and were baked: colours compiled in, repaint impossible without regeneration. Editing a token marked them stale and queued a job no attached agent was there to answer, which made the token panel appear to do nothing.

They were rebuilt as agent-authored token-driven HTML that links the project's own `tokens.css`. The effect was measured on the running server:

```text
accent #8A6A3B -> #1D6FA5    rendered .feature__mark  rgb(138,106,59) -> rgb(29,111,165)
accent restored              rendered .feature__mark  rgb(138,106,59)
staleTokens after both edits [false, false, false]
```

No agent, no regeneration, no staleness. The repaint is the CSS cascade.

### Fidelity to the approved screen

The build imports the same `tokens.css` the approved screens rendered from. Computed styles were compared between the approved screen and the shipped page at 1440px:

| Property | Approved screen | Built site |
| --- | --- | --- |
| Contract tokens | identical | identical |
| Body role | Inter, 17px, `rgb(34,36,31)` | Inter, 17px, `rgb(34,36,31)` |
| Display role | Instrument Serif, 88px, 400 | Instrument Serif, 88px, 400 |
| Page surface | `rgb(244,241,235)` | `rgb(244,241,235)` |

Two defects were found by this comparison and fixed rather than filed:

- The body role fell through to the framework's default sans stack at 16px. The contract's `--ls-font-body` and `--ls-text-body` now bind on `body`.
- The client-rendered application served an empty root, so the page was blank without JavaScript — a regression against the approved screen, which was plain HTML. The build now prerenders to static markup and hydrates.

## Comparability with the v1.1.0 run

The base prompt is byte-identical, so its digest test still holds. Three deltas must be stated when comparing scores:

1. **A design phase now exists.** v1.1.0 went from prompt to code in one step. v2.0.0 inserts a contract and a human review gate. Any quality difference is partly attributable to that, which is the point of the release rather than a confound to correct for.
2. **Tailwind v4 is an explicit tooling delta.** v1.1.0's runs used standard CSS as the base prompt suggests. The v2 build stage uses Tailwind v4 as a theme bridge over the contract's custom properties. The tokens remain plain CSS custom properties; the framework only maps them.
3. **The design-phase screens use a font service and remote images; the build must not.** The base prompt forbids remote fonts and images. Generated screens are a design artifact, reviewed as PNGs, and never shipped. The build self-hosts fonts and draws every visual locally. A reviewer checking the built result for remote assets is checking the right thing; checking the generated screens for them is not.

## Reproducing this run

```bash
cd /path/to/L.S.Design
python scripts/install.py --provider both --target ../orbit-one-v2
cd studio && npm ci && npm run build && cd ..
node studio/dist/server/cli.js init --project ../orbit-one-v2 --name "Orbit One"
# author ../orbit-one-v2/design/DESIGN.md from the base prompt's product facts
node studio/dist/server/cli.js --project ../orbit-one-v2 --port 4178 --open
node studio/dist/server/cli.js tokens --project ../orbit-one-v2 --emit stitch
# register the studio MCP entry in the target project, then drive the loop from the agent
node studio/dist/server/cli.js doctor --project ../orbit-one-v2
```
